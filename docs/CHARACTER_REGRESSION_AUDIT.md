# Cat and menu-guide regression investigation

## Finding

The reported severe slowdown was **not reproduced on the local server**. A read-only probe of `https://meryenda.aklitala.com` did expose a serious public delivery problem: the deployed 1,224,767-byte Phaser chunk was sent without gzip despite `Accept-Encoding: gzip`; one HTTP/2 download received only 48,836 bytes before timing out after 18 seconds. A 68,385-byte JavaScript chunk took 8.3 seconds to first byte and also timed out before completion. This can account for slow entry and failed dynamic imports even while Node is idle. The live site was serving an older hashed build during this probe; the local fixes below were not deployed. The exact point of failure in the public path—Nginx, TLS/HTTP/2, upstream or network route—still needs VPS-side logs and tests. The user's VPS measurements (nearly idle CPU, about 5.7 GB available RAM, 0.33 ms event-loop latency and 4 ms light-traffic HTTP p95) are consistent with a problem outside the measured Node request work, but do not prove its location.

Source inspection and browser isolation show that the cat and walking guide no longer have server simulations, database writes or character WebSocket events. Both run within the existing Phaser scene update loop and stop with that scene. The homepage does not load Phaser; it uses small CSS animations and a 15-second store-status check.

Git history provides a useful boundary. `dc6b74e` predates the cat and walking guide; `6362c1b` introduced both along with unrelated admin/menu work; `bf1d1af` and `a1ca837` optimized them. A detached archive of `dc6b74e` was built with the current installed dependencies. The total JavaScript requested by a fresh store browser grew from about 1,402 KiB before these features to about 1,420 KiB now. The largest chunk, containing Phaser, was already about 1,211 KiB before the cat and is about 1,225 KiB now. There are no new downloaded sprite sheets or uncompressed character images; these sprites are drawn into small Phaser textures at scene creation. The large Phaser download is a pre-existing initial-load cost, not a newly introduced cat asset. The supplied Nginx example now enables gzip for JavaScript and CSS. An isolated Nginx-to-Nitro test returned the current Phaser chunk in 393,299 bytes with `Content-Encoding: gzip`, versus 1,224,921 bytes uncompressed. The deployed proxy currently does **not** compress the inspected JavaScript assets.

Four fresh mobile-sized Chromium contexts were profiled against an isolated production build and disposable SQLite database, with 4× CPU throttling. A 2.5-second steady-state window showed approximately 60 FPS in every mode. In a reverse-order pass before the depth change, main-thread task time was 359 ms with both disabled, 364 ms with cat only, 373 ms with guide only, and 370 ms with both enabled. Later passes after the depth change varied more: both enabled cost about 449–461 ms versus 336–358 ms with both disabled, yet still held about 60 FPS. A separate 8× CPU pass measured 695 ms with both disabled and 714 ms with both enabled, also near 60 FPS. This variability means the short runs do not establish a stable per-feature CPU cost. Menu-button DOM opening took 5–11 ms in these passes. Cold canvas readiness ranged about 0.49–0.99 seconds across the 4× runs, strongly affected by run order and process/cache warm-up; it is not a reliable per-feature comparison. A before-features build reached its canvas in 0.76 seconds in a separate cold run and used 334 ms of main-thread task time over 2.5 seconds, about 60 FPS. These local runs cannot explain an extreme production slowdown.

One concrete avoidable cost was found in Phaser: `setDepth` queues a display-list sort even when the new depth equals the old one. The cat, yarn, guide, self avatar and moving remote labels called it repeatedly. They now call it only when depth actually changes. This removes unnecessary sorts during stationary frames and open dialogs; the short profiling windows did not show a reliable speedup beyond measurement noise. No new animation loop or Vue position watcher was added.

## Reversible isolation

The default remains both features enabled. A developer can compare `/store?cat=0&guide=0`, `/store?guide=0`, `/store?cat=0`, and `/store` after entering as a visitor. A disabled feature creates no sprite, texture, simulation instance, scene update work or pointer interaction. The Menu action remains usable when the guide is off; chat, presence, order tracking and menu data remain connected. Changing the query remounts only the Phaser component.
These switches do not remove the shared Phaser bundle from the store download; all four modes request the same approximately 1.2 MB uncompressed chunk. They isolate runtime work, so they cannot remedy a slow or stalled asset transfer.

For a site-wide temporary switch, set `NUXT_PUBLIC_STORE_CAT_ENABLED=false` and/or `NUXT_PUBLIC_STORE_GUIDE_ENABLED=false` in the PM2 process environment, then reload the process with `--update-env`. Remove the variables or set them to `true` to restore the default. The runtime cat switch was verified against a built production server: cat controls were absent without rebuilding. Existing `.env`, `.data`, credentials and SQLite business records were not changed.

## Module-load errors and remaining evidence

The root document now uses `Cache-Control: no-store` so a cached old SPA shell is less likely to reference removed hashed chunks after a deployment. Nuxt's one-time immediate chunk-error recovery is enabled. In an isolated browser test, the main game chunk was deliberately failed once: the browser made exactly one extra document request, fetched the chunk on retry and rendered the canvas without a page error. A normal load made one document request. The live probe did not reproduce `ERR_HTTP2_PING_FAILED` as a named browser error, but it did reproduce incomplete HTTP/2 JavaScript transfers. Keep old hashed assets available during deployment or use an atomic release so existing clients are not stranded between builds.

In two isolated browser sessions, pet/yarn interactions generated zero HTTP requests and zero character WebSocket frames. Both received a staff menu update and shared chat. A tap on the walking guide after 2.5 seconds opened the menu in about 1 ms from in-page pointer event to dialog DOM creation in a local headless run; Playwright's end-to-end click call took 30 ms. Six full page navigations with forced garbage collection left the measured JavaScript heap at 7–8 MiB without monotonic growth. Source review confirms that the Phaser game, visibility and reduced-motion listeners, socket, heartbeat, board timer and menu-day timer are cleaned up on unmount; a longer SPA-only navigation soak and physical-device memory check remain open.

Run a production browser network capture for any slow or failed visit. Record the exact failing `/_nuxt/*.js` URL, HTTP status, transfer size, cache headers, timing and console error, plus matching Nginx and PM2 logs. Verify that the proxy serves the same build's manifest and hashed files, enable JavaScript compression in the active HTTPS server block, and compare HTTP/2 and HTTP/1.1 from more than one network. A small live API probe returned in 5.36 seconds over HTTP/2 and 0.89 seconds over HTTP/1.1 in one paired run, but follow-up requests varied and timed out on both protocols; that is a clue, not proof of an HTTP/2-only defect. Test the four flags on an affected physical device; if only one mode is slow there, retain the relevant runtime switch while capturing a browser performance trace. Server CPU/RAM alone cannot rule out browser or edge-delivery problems.
